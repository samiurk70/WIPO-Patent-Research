# Counting-unit evidence

Generated by `python pipeline/counting_diagnostics.py` from the cached WIPO bulk
file. Regenerate rather than editing. Supports plan task 1.1 and §2.1/§2.2.

## 1. What WIPO's bulk file does about multi-field patents — **whole counting**

Task 1.1 asks this explicitly, and it is answerable from the primary source.
Schmoch (2008), *Concept of a Technology Classification for Country Comparisons*,
the concordance WIPO applies to this file, states that because IPC8 does not
distinguish main from secondary classifications, **"all classifications of the
applications were taken into account"**, and that the resulting **"overlap or the
double counting rate is at a level of 20 percent"**. Schmoch notes that restricting
to first codes is possible and that the relative distribution across fields is
largely unchanged either way.

This is whole counting, not fractional: a patent spanning three fields is counted
once in each. Confirmed against the data — every `count` value in the file is an
integer, which fractional counting could not produce.

**Consequence for the manuscript.** Summing over the 35 fields overstates the total
by roughly the double-counting rate, and the green *share* is inflated for patents
straddling environmental and non-environmental fields. The share is the more robust
of the two, but the inflation is not zero and it has never been stated. Section 3.2
must say the file uses whole counting and cite Schmoch (2008) for the 20% figure.

## 2. The office code `**` is the PCT international phase, and it is being added

`**` is not a total: for any slice, the sum over the named offices exceeds it.
Its yearly volume (309,728 in 2020) and its origin profile (JP, US, CN, KR, DE at
the top) match published PCT international applications, not an aggregate.

`build_dataset.py` sums over every office, so a PCT-routed invention is counted
once for its international publication **and** again for each national-phase
publication. This is a second layer of duplication on top of the multi-office one,
and it is not mentioned anywhere in the manuscript.

**This is the whole problem in one table.** China's count is 91.7% domestic filings at CNIPA, so deduplicating barely touches it. Singapore's is 4.0% domestic: almost its entire count is the same inventions published again at foreign offices, and deduplication collapses it toward its family count.

So moving to families does **not** narrow the reported gap. It widens it, exactly as
§2.1 predicts. The headline "two to four orders of magnitude" is likely to become
larger, not smaller, and every adjective attached to it has to be rewritten.

A country showing 0.0% at its own office does not file domestically at zero rate —
it means WIPO's file carries no origin-resolved rows for that office, which is
itself worth a footnote when Table 3 reports those countries.

## 4. Option A's data source does not exist in scriptable form

The locked decision was Option A: RQ1 capacity at family level, using "WIPO's own
country-level patent-family indicator series". That series is **not** in any bulk
download. Checked on 2026-09-02:

- `wipo-data-patent-indicators.zip`, the file this pipeline already caches, holds only
  indicators 4 and 5 (publications and grants by technology). No family series.
- The bulk-download listing on wipo.int offers exactly three complete indicator sets —
  patents, trademarks, designs — and the patent one is the file above.
- The Statistical Country Profiles (PDF, per country) report applications, PCT filings
  and rankings. No family counts.
- The IP Statistics Data Center at `www3.wipo.int/ipstats/` is a single-page
  application whose data comes from an undocumented private API (`/api/v1/public`)
  built in lazy-loaded chunks. The legacy `keyindex.htm` entry point now returns the
  same application shell.

WIPO does publish the series — through that interface, by hand.

### Why not script it anyway (checked 2026-09-02, and the first answer was too weak)

The app's endpoints are findable: the lazy-loaded chunks name
`/api/v1/public/ips-search` and `/api/v1/public/keyindicator` against a base host of
`api.ipstatsdc.deda.prd.web1.wipo.int`, which resolves and answers. Getting the data
that way is a solvable problem, not an impossible one.

The **reproducibility** objection is not the reason to decline, and it was overstated
when first written here. Fetching once and caching the result under `data/raw/` with a
checksum produces exactly the artefact the manual export produces. Nobody re-downloads
it either way, so the deposit is identical and nothing breaks for a reviewer.

The reason is **permission**. `https://www3.wipo.int/robots.txt` is:

```
User-agent: *
Disallow: /
```

A blanket disallow on the whole host. WIPO's general terms of use carry no explicit
anti-scraping clause, but robots.txt is an unambiguous, machine-readable statement of
what the operator wants from automated clients, and the API host is internal
infrastructure naming (`deda.prd.web1`) rather than a published interface.

A person using the interface it was built for is not an automated client. That is the
whole distinction, and it is why the export is a human task rather than a script.

**This is a decision for the authors, not a blocker to code around.** The options and
the recommendation are in `docs/phase0_decisions.md`.
